# lss 2.0: modular, hardened server setup

Status: approved 2026-10-13. Replaces `install-configure-script.bash` (1.x).

## Goal

One tool that turns a fresh Linux server into a hardened, production-ready machine for any kind of company. It runs
every module with one command, a chosen profile, or single modules. Everything listed here works on every supported
distribution and is tested there; anything that cannot be tested does not ship.

## Supported systems

Debian 12 and 13, Ubuntu 22.04 and 24.04, the RHEL family 9 and 10 (Rocky Linux, AlmaLinux, RHEL). x86_64 and
aarch64. Requirements: root, systemd, bash 5, 1 GB RAM (2 GB for profiles with apps, 4 GB for `all`).

## Architecture

```text
lss                          entry point, installed as /usr/local/sbin/lss
lib/*.sh                     core: log, os, config, pkg, repo, fetch, service, firewall, secrets, template, backup,
                             state, module, ui
modules/<group>/<name>.sh    one module per file
profiles/<name>.conf         module lists with settings
templates/<module>/...       configuration templates
data/checksums.txt           SHA-256 of every direct download, data/keys/ GPG keys with pinned fingerprints
ansible/                     collection vectode.lss
bootstrap.sh                 downloads, verifies and installs a release
tests/unit, tests/integration
```

Installed layout: code in `/opt/lss/<version>` (root-owned, 0755, symlink `/opt/lss/current`), configuration in
`/etc/lss/lss.conf` (0600), secrets in `/etc/lss/secrets/<name>` (0600, directory 0700), state in
`/var/lib/lss/`, backups of changed files in `/var/lib/lss/backup/<run id>/`, logs in `/var/log/lss/` and the
journal (identifier `lss`).

### Module contract

A module file sets metadata variables and defines functions. It is only ever sourced in a subshell, so modules
cannot leak state into each other.

| Variable          | Meaning                                                                      |
| ----------------- | ---------------------------------------------------------------------------- |
| `MOD_NAME`        | module name, equal to the file name                                          |
| `MOD_GROUP`       | base, security, web, runtime, database, container, mail, apps, network, ... |
| `MOD_DESCRIPTION` | one line                                                                     |
| `MOD_REQUIRES`    | modules installed first                                                      |
| `MOD_CONFLICTS`   | modules that cannot be installed together with this one                     |
| `MOD_MODES`       | `native`, `docker` or both                                                   |
| `MOD_PORTS`       | ports opened in the firewall, with scope `public`, `vpn` or `local`          |
| `MOD_OPTIONS`     | `KEY|default|description` entries, read as `LSS_<MODULE>_<KEY>`               |
| `MOD_SECRETS`     | secrets the module generates                                                 |

| Function        | Contract                                                                          |
| --------------- | --------------------------------------------------------------------------------- |
| `mod_check`     | validate options and preconditions; no changes                                    |
| `mod_install`   | install packages or images; idempotent                                            |
| `mod_configure` | write configuration from templates, back up replaced files, test before reloading |
| `mod_verify`    | prove the module works (service active, port answers, functional probe)           |
| `mod_remove`    | stop and remove the module, keep data unless `--purge`                            |

The core resolves `MOD_REQUIRES` into an order, refuses conflicts before the first change, runs
check for all modules first, then install, configure and verify per module. A failing step restores the backed-up
files of that module and stops the run with a clear message. Every run is idempotent: a second run changes nothing
and reports so.

### Command line

```text
lss                               interactive menu (whiptail)
lss list [--group g]              modules with state
lss info <module>                 description, options, ports, requirements
lss install <module...|all>       install modules (plus requirements)
lss install --profile <name>      install a profile
lss configure <module>            rewrite configuration from current settings
lss verify [module...]            run verify of installed modules, detect changed managed files
lss status                        installed modules, versions, failed services
lss remove <module> [--purge]     remove a module
lss audit                         Lynis audit with hardening index and report
lss update                        update lss itself from a verified release
lss secrets show <name>           print a generated secret (root only)
Options: --config FILE, --mode native|docker, --set KEY=VALUE, --dry-run, --yes, --verbose, --no-color
```

Settings precedence: `--set`, environment, `--config`/`/etc/lss/lss.conf`, profile, module default. The
configuration file is parsed as `KEY=value` lines and never sourced.

Conflicts: nginx/apache/caddy (one web server owns 80/443), fail2ban/crowdsec, docker/podman, mariadb/mysql,
redis/valkey, netdata/prometheus stack is allowed together. Apps run as Docker Compose stacks behind the installed
web server; services with an upstream package also offer `native`.

Profiles: `minimal-secure` (base + security), `webhosting` (+ nginx, tls, php, mariadb, phpmyadmin, restic),
`office` (+ nextcloud, collabora, vaultwarden, mailserver, webmail), `devops` (+ docker, forgejo, monitoring stack),
`k8s-node` (+ k3s), `all` (one choice per conflict group, see `profiles/all.conf`).

Known limits, stated in the documentation: `mailserver` needs correct MX, SPF, DKIM, DMARC and reverse DNS, which
lss prints but cannot set; `tls` with Let's Encrypt needs a public domain (tests use Pebble).

## Security model

- No `curl | bash`. Third-party repositories are added with a key whose fingerprint is pinned in `data/keys/`,
  restricted with `signed-by` (apt) or `gpgkey` + `gpgcheck=1` (dnf). Direct downloads are checked against
  `data/checksums.txt`.
- Default closed: inbound only SSH plus the public ports of installed modules. Admin UIs (phpMyAdmin, Adminer,
  pgAdmin, Portainer, Grafana, Prometheus, Netdata) bind to localhost or the WireGuard network; public exposure needs
  an explicit option and then gets basic auth and a fail2ban/crowdsec jail. Databases bind to 127.0.0.1 or an
  internal Docker network.
- Each service runs as its own user; systemd drop-ins add sandboxing (`NoNewPrivileges`, `ProtectSystem=strict`,
  `PrivateTmp`, ...) where the service tolerates it. Containers: images pinned by digest, `no-new-privileges`,
  `cap_drop: [ALL]` plus needed capabilities, read-only root where possible, memory and PID limits, no Docker socket
  in app containers.
- TLS: Mozilla intermediate (TLS 1.2 and 1.3), HSTS, OCSP stapling, security headers, renewal timer with test.
- Hardening baseline: CIS Level 1 server items plus DISA STIG items that keep a server usable; deviations explained
  in `docs/hardening.md`. Target Lynis hardening index 85 or more after `minimal-secure`.
- Lockout protection: `ssh-hardening` only disables passwords after a key for a sudo user exists and `sshd -t`
  passes; firewall activation over SSH arms a 120-second rollback that is cancelled once the SSH rule is confirmed.
- Secrets: generated with 32+ random characters from `/dev/urandom`, stored only in `/etc/lss/secrets`, passed to
  containers as files, masked in logs. Nothing secret appears in command lines, process lists or compose files.

## Security in operation

Hardening is not a one-time step. The `guard` module (part of `minimal-secure` and every profile) keeps the server
at the level lss set up and reports every deviation:

- Daily `lss verify` of all installed modules: a stopped service, a failing probe or a managed file changed outside
  lss is reported; drifted security settings (sshd, sysctl, firewall, auditd rules, systemd sandboxing) are put
  back automatically unless `LSS_GUARD_AUTOFIX=false`.
- Security updates every day (unattended-upgrades or dnf-automatic), restarts of affected services
  (needrestart / `dnf needs-restarting`), and a reboot in a configurable window when the kernel or libc changed.
- Daily AIDE integrity check, rkhunter and ClamAV scans where installed; weekly Lynis audit with the hardening index
  tracked over time; a drop below the threshold is an alert.
- Vulnerability check of installed packages (debsecan on Debian/Ubuntu, `dnf updateinfo --security` on RHEL) and of
  container images (Trivy) every day.
- Certificate expiry, backup age and the weekly restore test, disk space, failed logins and fail2ban/crowdsec bans
  are watched as well.
- Alerts go to e-mail (through `mail-relay`) and optionally to a webhook (Slack, Teams, Discord, ntfy); a daily
  summary lists what was checked. Everything also lands in the journal and, with the monitoring stack, in Prometheus.
- `lss update` keeps lss itself current from verified releases, so new hardening rules reach existing servers.

## Testing

- Static: ShellCheck (all optional checks that apply), shfmt, actionlint, zizmor, REUSE, Gitleaks, Semgrep.
- Unit: bats-core for `lib/`, coverage with kcov, at least 90 % of lines.
- Integration: every module on all six distributions in systemd containers (privileged where the module needs it):
  install, verify, install again without changes, remove. Modules needing a real kernel (firewall, wireguard, k3s,
  mac, auditd, kernel-hardening, usbguard) run on GitHub-hosted Ubuntu VMs and in QEMU VMs for Debian and Rocky.
  TLS against Pebble, mail flow locally (send, receive, DKIM signature, spam check).
- Nightly: `--profile all` on every distribution, then `lss audit` with the Lynis threshold.

## Repository and releases

Like Self-Updater, ExpressJS-Template and ID-Generator: community files, GOVERNANCE, SECURITY with support period,
REUSE/SPDX headers, ruleset on `main` and on `v*` tags, only `main`, DCO, Scorecard, Dependabot with auto-merge,
SonarCloud, Semgrep and ShellCheck SARIF in code scanning, public GitHub Project, Discussions, OpenSSF Best
Practices (passing, silver, baselines, as much gold as possible).

Releases: merging a pull request into `main` releases automatically (SemVer from labels), signed tag, release
archive, `SHA256SUMS`, Sigstore attestation, SBOM. `bootstrap.sh` and `lss update` verify checksum and attestation
before running anything. The Ansible collection is built with every release.

## Stages

Each stage is one or more pull requests with green CI; `main` stays usable.

1. Core (`lib/`, `lss`, module runner, tests, CI) and repository setup; modules of base and security.
2. web, runtime, database.
3. container including k3s.
4. backup, monitoring, network.
5. mail.
6. apps.
7. Ansible collection, bootstrap, documentation, release 2.0.0 (removes the 1.x script, with upgrade notes).
